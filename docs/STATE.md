### Resolved design decisions (from S0)

| Q | Resolution | Source |
|---|------------|--------|
| Q1 — Restore on empty vs populated local | Same Dexie transaction flow; **different confirmation copy + button styling**. Empty: neutral "Populate". Populated: destructive "Replace local data" with data-loss warning. | `L1-GITHUB.md` → "Restore from GitHub (S2)" |
| Q2 — Payment derived fields on Restore | **Trust JSON, do not recompute.** Fields are persisted-at-log-time, not live-derived. Recomputation would silently disagree with reality (extra-principal payments, edits). Snapshot validation rejects payments missing them. | `L1-GITHUB.md` → "Open question resolutions" |
| Q3 — PAT failure modes | 7-row mapping table covering 401, 404 on repo, public-repo refusal, 404 on data.json (first-run, not error), token revoked mid-flow, rate limit, network error. Each has copy + recovery action. | `L1-GITHUB.md` → "Open question resolutions" |
| Q4 — Integrity check field | **Yes — `recordCounts` field.** Restore validates array lengths match before touching Dexie. `appVersion` also included as diagnostic-only field for `git log` debugging. | `STORAGE-FORMAT.md` → "Top-level shape" |

Additional decisions surfaced during S0:
- **Sync status detection:** dirty-bit on first cut (Pinia, flipped on any Dexie write, cleared on successful sync). Hash-based detection only if dirty-bit churns too much.
- **`deviceId` format:** `${platform}-${YYYY-MM-DD}` of first Connect, where platform = `phone | tablet | desktop` via matchMedia + UA heuristic. Used in commit messages + JSON snapshot for diagnostics.
- **Public-repo refusal:** Connect validates `repos/{o}/{r}.private === true` and refuses with explicit copy. Defense in depth — PAT scoping should prevent reaching a public repo, but a misconfigured PAT shouldn't quietly write personal data to a public repo.
- **Entity array key naming:** `marketEntries` (camelCase, matches Dexie table name 1:1) rather than `market_entries` from the deferred Sheets plan. Zero key-mapping in Restore/Sync code.

- **2026-04-27** — **L1 — S3 hotfix: DataCloneError on Restore (shallowRef).** User report: clicking "Replace local data" in `ConfirmRestoreModal` raised `DataCloneError: Failed to execute 'add' on 'IDBObjectStore': #<Object> could not be cloned` and the restore aborted — modal stayed open, no rows applied. Root cause: `pendingRestore` declared as `ref<PendingRestore | null>(null)` at `src/stores/sync.ts:56`. When `fetchAndPrepareRestore` assigned `pendingRestore.value = { snapshot, ... }`, Vue 3 deep-reactivized the snapshot, wrapping every nested array and object in a `Proxy`. `applyPendingRestore` then passed `snapshot.commitments` (Proxy of Array of Proxies) directly to `db.commitments.bulkAdd(...)`. IndexedDB's structured-clone algorithm rejects Vue 3 reactive Proxies — even though their get traps return underlying values, the cloner sees `[object Array]` as non-structured-cloneable. **Reproduction**: mirrored the live assignment in browser-preview eval; confirmed `bulkAdd(arr)` and `structuredClone(arr)` throw the same `DataCloneError`. Confirmed `bulkAdd(JSON.parse(JSON.stringify(arr)))`, `bulkAdd(arr['__v_raw'].map(c => c['__v_raw']))`, and `bulkAdd([...arr].map(c => ({...c})))` all succeed — proving the Proxy wrap is the only fault. **Fix**: change `ref` → `shallowRef` for `pendingRestore`. The pending object is a one-shot handoff to `applyPendingRestore`; nothing mutates fields-by-field after assignment. Modal consumers read only `remoteCounts`/`localCounts` scalars, so deep reactivity isn't needed. Pinia subscribers still fire on value-replacement (verified — modal v-if appears/disappears on assign/clear). `inFlight`, `dirty`, `syncError`, `restoreError`, `pendingConflict` retain plain `ref` since their values are scalars. **Verification**: full `applyPendingRestore` path with 12-intention snapshot through live store: 12 rows written, `pendingRestore` cleared, `lastKnownSha` persisted, no errors thrown. 37/37 vitest pass, vue-tsc --noEmit clean. **Follow-up flagged**: `pendingConflict` ref at sync.ts:57 has identical hazard — when S4 wires the conflict modal it will likely write `remoteSnapshot.commitments` to Dexie during merge; apply same `shallowRef` treatment then. **Diagnostic clarity for the user**: surfaced that "instant sync" between installed PWA and live tab on the same origin is shared IndexedDB, not GitHub round-trip; and that `Sync now` is one-way push (local→GitHub) and `Restore` is one-way pull (GitHub→local) — order-of-operations footgun if Sync from a sparse-state device runs before Restore.
